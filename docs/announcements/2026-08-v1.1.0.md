# Announcement drafts — fluFrame v1.1.0 (launch)

Ready-to-post drafts for the **first real launch push**. The v0.8.0 draft
was never posted; this supersedes it. The EN version targets r/FlutterDev
and X, the KO version targets Korean Flutter communities (오픈카톡 / 네이버
카페 / OKKY / GeekNews).

The hook is no longer "another boilerplate". It is **a boilerplate that
can still update your app six months after you generated it** — that is
the part nothing else in the Flutter starter space does, and it is what
1.0's stability contract exists to support.

## English — r/FlutterDev

**Title**: fluFrame 1.1 — a Flutter starter you can still pull updates
from after you've generated your app

**Body**:

Every Flutter boilerplate I tried had the same end state: you generate
once, the template moves on, and your app is permanently forked from it.
So I built **fluFrame** with an upgrade path as the actual design
constraint.

```sh
dart pub global activate fluframe
fluframe create my_app --org com.mycompany --backend supabase
cd my_app && flutter run --dart-define-from-file=env/dev.json

# six months later
fluframe upgrade          # dry-run: shows exactly what would change
fluframe upgrade --apply  # three-way merge, git conflict markers, no silent deletes
```

`upgrade` reconstructs the *original* template from the pub.dev archive of
the version you generated with, then does a per-file three-way merge
against the new one. Your edits survive. Conflicts get normal git markers
instead of being guessed at. Nothing is ever deleted without telling you.

What you get out of `create`, already wired and passing 59 tests:

- **Riverpod 3** — manual `Notifier`/`AsyncNotifier`, no provider codegen
- **go_router 17** — `StatefulShellRoute` bottom tabs, nested routes,
  return-path redirects
- **Auth scaffold** — email/password login, gated profile tab, persisted
  session, all behind one `AuthRepository` seam. `--backend supabase` or
  `--backend firebase` wires the real SDK; omit it and keep the offline fake
- **freezed 3 + json_serializable** models, dio with typed error mapping,
  and an offline fallback cache on the REST sample
- **Material 3 theming** — 6 persisted colour presets, light/dark
- **Localization** — English, Korean, Japanese
- Flavors via `--dart-define-from-file`, `very_good_analysis` at zero issues
- Optional addons that stack: `--error-reporting sentry`,
  `--analytics amplitude` (with automatic screen tracking)

Two full example apps built with it are in the repo (a persistent todo app,
and a weather app hitting a real keyless API), and both are analyzed and
tested in CI on every commit — as is every generated variant. A release
cannot ship unless the app it generates passes `flutter analyze` and
`flutter test` first.

1.0 came with a written public contract and a deprecation policy, so the
CLI surface, generation guarantees, and the upgrade path are all under
semver now. pub.dev score is 160/160.

- pub.dev: https://pub.dev/packages/fluframe
- GitHub: https://github.com/JoGyoungJun/fluFrame

I'd genuinely like to know what would block you from starting a real
project on this. Issues and PRs very welcome.

## 한국어 — 커뮤니티용

**제목**: 앱을 생성한 뒤에도 템플릿 업데이트를 계속 받아올 수 있는 Flutter
스타터 fluFrame 1.1을 공개합니다

**본문**:

Flutter 보일러플레이트를 여러 개 써봤지만 끝은 늘 같았습니다. 한 번 생성하면
템플릿은 앞으로 나아가고, 내 앱은 그 시점에서 영구히 갈라집니다. 그래서
**fluFrame**은 업그레이드 경로를 설계 제약으로 두고 만들었습니다.

```sh
dart pub global activate fluframe
fluframe create my_app --org com.mycompany --backend supabase
cd my_app && flutter run --dart-define-from-file=env/dev.json

# 6개월 뒤
fluframe upgrade          # 기본은 dry-run — 무엇이 바뀔지만 보여줍니다
fluframe upgrade --apply  # 3-way 병합, git 충돌 마커, 임의 삭제 없음
```

`upgrade`는 여러분이 생성할 때 썼던 **그 버전의 템플릿**을 pub.dev 아카이브에서
복원한 뒤, 새 템플릿과 파일 단위로 3-way 병합합니다. 직접 수정한 코드는
살아남고, 충돌은 추측하지 않고 평소 쓰는 git 충돌 마커로 넘겨줍니다. 파일이
사라질 때는 반드시 먼저 알려줍니다.

`create` 직후부터 59개 테스트가 전부 통과하는 상태로 다음이 들어 있습니다:

- **Riverpod 3** — 수동 `Notifier`/`AsyncNotifier`, 프로바이더 코드젠 없음
- **go_router 17** — `StatefulShellRoute` 하단 탭, 중첩 라우트, 복귀 경로 리다이렉트
- **인증 스캐폴드** — 이메일 로그인, 게이팅된 프로필 탭, 재시작에도 유지되는
  세션. 전부 `AuthRepository` 하나로 추상화되어 있고 `--backend supabase` /
  `--backend firebase`로 실제 SDK까지 연결됩니다(생략하면 오프라인 페이크 유지)
- **freezed 3 + json_serializable** 모델, 타입 매핑된 dio 에러 처리, REST
  샘플의 오프라인 폴백 캐시
- **Material 3 테마** — 영속화되는 색상 프리셋 6종, 라이트/다크
- **다국어** — 한국어, 영어, 일본어
- `--dart-define-from-file` 플레이버, `very_good_analysis` 경고 0건
- 조합 가능한 애드온: `--error-reporting sentry`, `--analytics amplitude`
  (화면 추적 자동 연결)

이걸로 만든 예제 앱 2개(영속 투두 앱, 실제 키 없는 API를 쓰는 날씨 앱)가
저장소에 있고, 모든 커밋에서 CI가 분석·테스트합니다. 생성되는 모든 변형도
같습니다 — 생성된 앱이 `flutter analyze`와 `flutter test`를 통과하지 못하면
릴리스가 나가지 않습니다.

1.0에서 공개 계약과 디프리케이션 정책을 문서로 확정했기 때문에, CLI 표면과
생성 보장, 업그레이드 경로가 모두 semver 아래에 있습니다. pub.dev 점수는
160/160 만점입니다.

- pub.dev: https://pub.dev/packages/fluframe
- GitHub: https://github.com/JoGyoungJun/fluFrame

실제 프로젝트를 이걸로 시작하려 할 때 무엇이 걸림돌일지 의견 주시면 정말
감사하겠습니다. 이슈와 PR 모두 환영합니다.
